# Shield for Safari

Safari port of [Shield](../chrome-adblock), the ad, tracker, cryptominer, malware and phishing blocker. Same rulesets and popup as the Chrome version, wrapped in the macOS app Safari requires.

Requires Safari 18 or later on macOS 14 or later.

## Install

1. Download `Shield-<version>.zip` from [Releases](https://github.com/livid/safari-adblock/releases/latest), unzip it, and move **Shield** to Applications. The app is notarized by Apple.
2. Open Shield and click "Quit and Open Safari Settings…". Turn on **Shield** and set "Allow on every website".

Shield checks for updates when you open the app, and daily while it stays open. You can also choose Shield → Check for Updates…. Updates come from this repository's releases, signed with Shield's own update key.

## Layout

| Path | What it is |
| --- | --- |
| `extension/` | The web extension (manifest, background worker, popup, warning page, compiled rules). The Xcode project references these files directly, so edit them here. |
| `Shield/` | Xcode project for the container app and the Safari extension target, generated by `safari-web-extension-packager`. |
| `tools/build-rules.mjs` | Regenerates `extension/rules/` and `extension/cosmetic/` from Brave's default filter lists (`node tools/build-rules.mjs`). |
| `tools/count-webkit-rules.swift` | Measures what each bundled ruleset costs under Safari's rule limit and writes `extension/rules/webkit-rule-counts.json`. Run it (`swift tools/count-webkit-rules.swift`) after every rule rebuild. |
| `tools/custom-filters.txt` | Shield's own filters, compiled in alongside the lists. |
| `tools/release.sh` | Builds, notarizes and publishes a release with its Sparkle appcast (see [Releasing](#releasing)). |
| `tools/verify-update-signature.swift` | Checks an update's EdDSA signature against the public key in the app; used by `release.sh`. |

## Build and run locally

Both targets are signed automatically with team `66KP7KX9MX` (Apple Development for builds run locally).

```sh
xcodebuild -project Shield/Shield.xcodeproj -scheme Shield -configuration Debug \
  -derivedDataPath build -allowProvisioningUpdates build
open build/Build/Products/Debug/Shield.app
```

Over SSH the login keychain is locked and codesign fails with `errSecInternalComponent`. Unlock it in that session first with `security unlock-keychain ~/Library/Keychains/login.keychain-db`.

Then in Safari: Settings → Extensions → enable **Shield**, and set "Allow on every website". Safari asks per site otherwise, and element hiding needs the access.

Without a signing identity, build ad-hoc instead (`CODE_SIGN_IDENTITY=- CODE_SIGN_STYLE=Manual DEVELOPMENT_TEAM=`). Safari then loads it only with Settings → Developer → "Allow unsigned extensions" on, and turns that off every time it quits.

## Releasing

Releases are Developer ID builds, notarized by Apple, published as GitHub releases. Installed copies find them through [Sparkle](https://sparkle-project.org) (2.10.1, a Swift package in the Xcode project). The app reads `https://github.com/livid/safari-adblock/releases/latest/download/appcast.xml`, which always points at the newest release's `appcast.xml`.

```sh
# bump "version" in extension/manifest.json, then commit and push
tools/release.sh --notes notes.md     # Markdown notes, for GitHub and the update dialog
tools/release.sh --dry-run            # everything except publishing; output in dist/
```

The script refuses to publish uncommitted or unpushed code, or a version that already has a release. It checks the Developer ID signatures and that notarization and Gatekeeper accept the app. Before uploading, it confirms that the update's signature verifies against the public key inside the app. The build number Sparkle compares is the commit count.

One-time setup on the Mac that releases:

- **Notarization login:** a notarytool keychain profile for team 66KP7KX9MX, named `exe-notary` (the one this Mac already has), or set `NOTARY_PROFILE`. To create one: `xcrun notarytool store-credentials exe-notary --apple-id <Apple ID> --team-id 66KP7KX9MX`, which asks for an [app-specific password](https://account.apple.com/account/manage).
- **Update signing key:** stored in the login keychain under the account `io.github.livid.Shield`. Its public half is `SUPublicEDKey` in `Shield/Shield/Info.plist`. **Back it up**: without it, installed copies can never be updated again. Export it with `tools/.sparkle/2.10.1/bin/generate_keys --account io.github.livid.Shield -x <file>`, keep the file somewhere safe, and import it on another Mac with `-f <file>`.
- **gh**, logged in, to create the release.

Over SSH, unlock the login keychain first (`security unlock-keychain ~/Library/Keychains/login.keychain-db`). Signing and notarization both need it.

## How Safari differs, and what Shield does about it

These were measured on Safari 27.2 (in Safari itself, and with WebKit's own rule translator and compiler), not taken from documentation.

- **One rule list, capped at 150,000.** Safari compiles every enabled rule (bundled, downloaded and per-session) into a single WebKit content blocker of at most 150,000 rules, and writes each `requestDomains` entry out as its own rule. The bundled lists use 119,528, so the background fills the rest by importance: paused sites, then dangerous sites, then the downloaded ad list, leaving out ad-feed hosts the bundled lists already block. Today everything fits. If a list grows past the limit, the popup says how many domains were left out.
- **Every rule change takes 20–40 seconds.** Safari recompiles the whole list for any change. Pausing a site shows "Applying…" and reloads the tab when it's done. "Open the site anyway" shows "Opening…" for the same reason.
- **The background worker is stopped 30 seconds after its last event**, even mid-call. Rule updates are therefore resumable: a run that was cut off is finished on the next wake without compiling again. The warning page adds its own allow rule instead of asking the worker to.
- **No redirects for page loads.** Safari ignores redirect rules for top-level navigations: extension paths, plain URLs and query rewrites alike. It also drops `requestDomains` from any rule that has a `regexFilter`, which would turn the Chrome version's warning-page rule into "redirect every site". So Shield blocks dangerous sites outright (all request types, one rule per domain) and sends the tab to the warning page itself. The page gets the address in its fragment and has the background confirm it's on a threat list.
- **No tracking-parameter stripping.** That feature was built entirely on page-load redirects, so it's gone from the Safari version, and so is its toggle. Safari's own Settings → Advanced → "Use advanced tracking and fingerprinting protection" in all browsing removes known tracking parameters.
- **Lifetime totals** come from `getMatchedRules`, which in Safari lists blocked requests with only an address, tab and time. The background adds them up from a stored position whenever a page finishes loading, a tab closes or the popup opens, and once more a minute after the last page load. Since Safari doesn't say what kind of request was blocked, "data saved" is estimated from each address's file extension.
- **Resource types `object` and `webtransport` don't exist in Safari.** A rule listing only those is invalid, so they're never emitted. The committed rules came from the Chrome build with those types stripped. Rerunning `tools/build-rules.mjs` produces the same thing directly, and also evaluates list `!#if` blocks as `env_safari` instead of `env_chromium`.

Problems show up in the extension's background console (Develop → Web Extension Background Content → Shield) as `Shield:` warnings, and in Safari's log under `com.apple.WebKit:Extensions`.
